# Sparse staging prepared in one reference pass

Current status: **rejected** after 115 tests, old38/76 full code identity, actual single-kernel Graph and three sanitizers passed. Short100GB reductions were +0.0109% and -0.7015%;50GB +3.0985%. Actual unique traffic fell about3.5% because pool admission order changed, so the50GB improvement cannot be attributed entirely to pass fusion. See `decisions.json`, `miss_comparison.json`, `checkpoint_audit.json` and the [report](../../../docs/mla_host_a100_sparse_prepare_20261101.md).

This independent candidate starts from retained production CPEa436. It is not adopted. `manifest.json` binds the frozen source and scope. The old original kernels, dispatch and math remain literal.

Each temporary batch pool owns a staging range beginning at `pool_row_start * max_kv_len`; unique claims allocate warp ranks inside it. The owner publishes all eight pages it claimed before any thread waits for other owners. Prepare writes the final negative staging remap directly. A bounded scan of pool counts replaces the later full pass over Host references. Dense fetch jobs map to the sparse physical slots, including the original derived16/64 row choice; original overlapped LRU selection and shared→staging→cache copying remain.

The new branch additionally requires positive maxK divisible by256. On the original large-row dispatch, prepare_parts is one and prepare_segment equals maxK, so every pool range is bounded by its rows' total capacity and aligned for both16/64-row flags. The existing host_items array stores copied pool counts; row_slot_base stores dense-job prefixes. Counts are copied before the original claim-reset phase. No new allocation, kernel or grid barrier is added.

Admission order within a pool changes from row-rank order to warp arrival order. The original exact LRU stamp selection, current-launch hit protection and unique-page admission limits remain; this does not claim identical victim/page states between independently scheduled launches. All changed hit/miss counts and actual payloads must be checked and reported. Inline owner waits, pool allocation contention, binary-search job mapping and altered locality may outweigh the saved pass. These are hypotheses until validated.

`precompile_review/` preserves an uncompiled initial draft that hardcoded64-row jobs; code review corrected it before either GPU build. `sparse_job_review.json` independently checks physical slot/flag bounds and dense-job mapping for supplied pool counts; it is not GPU correctness or performance evidence. Test, stress, codegen, actual Graph, sanitizer and screen states track actual execution. Never duplicate live producers or overwrite frozen headers/raw data.
