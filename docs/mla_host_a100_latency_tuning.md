# A100 第四轮：减少高延迟链路上的等待轮数（2026-10-29）

基线为 `109b1c76`，本轮继续保留单 cooperative kernel、4096 槽/请求、精确 LRU、相同 top-k 和 BF16 KV，没有修改带宽/延迟模拟器。重点是 50/100 GB/s、20 µs 条件下缩短小 batch 与纯 device attention 的差距。

## 最终改动

1. **小 batch 的每行结果完成后即可合并。** staged＋缓存、至多 32 个 `(query 行, 64-head tile)` 时，attention item 写完 partial 后先用每线程 fence 和 CTA barrier 发布数据，再增加该行完成计数；merge CTA 用 acquire 读取计数，只等待自己所读行的全部有效 partial。worker 先走完自己的全部 attention item 再进入 merge，因此等待者不会持有尚未发出的任务。大 batch、无缓存及原地读保持原 grid barrier。
2. **完成计数使用独立 workspace。** 内部 state 增加每行一个 int32，并由最后离开的 CTA 清零。不能复用 prepare claim 计数：其他 CTA 离开 resolve barrier 后仍在清零它，存在与新完成计数相撞的可能。不会将初筛原型的计数协议带入最终实现。
3. **小 batch 更早切换到 64 行取数块。** fetch CTA 数大于 8、query/head tile 数至多 32 时，若 16 行块需要第二轮，则切换到 64 行块，减少依赖访问等待次数。大 batch 和至多 8 个 fetch CTA 沿用上一版阈值。各方法的模拟字节数、带宽和访问延迟不变。

## 筛选和局限

- 先在真实 assistant 的 256 连续位置上扫描 f16/f32、h64/h256/h1024 和 host_split，保留所有原始数据。这只是参数筛选，不能替代随后完整 1024 位置的旧/新代码对照。
- 在较多 MTP 行自动使用 h256，有部分代理收益，但真实数据收益不稳定，部分较大 batch 回退，未采用。MTP1 四请求和 MTP8 单请求分别为 4 行和 8 行；MTP8 128 请求为 1024 行，属于大 batch。
- 初版新增测试在填入 padding 后误从同一索引存储恢复，四个新用例因此失败；改成在填入前保存独立副本后，通过数学参考检查。保留初次失败日志，不把它计为通过。
- 本轮仍是 kernel 和单层回放优化；没有提前读取未来 token 的 trace，没有增加缓存容量或改变 LRU，不将某一 batch 的收益外推到全部配置。

## 验证与复现

最终 **91 项测试通过**（70.35 秒）。反向顺序复测的 100 GB/s＋20 µs、固定 f16/h64 代理 trace：MTP1 四请求 94.14→77.38 µs（−17.8%），MTP8 单请求 101.89→90.11 µs（−11.6%），四请求 246.78→231.42 µs（−6.2%）。这些配置仍分别约为纯 device 下限的 1.68 / 1.83 / 2.09 倍，距离目标还有明显差距。

**没有普遍加速，也没有隐去回退。** MTP8 128 请求（1024 行）的代理 trace、100 GB/s＋20 µs：5554.69→5713.92 µs，慢 2.9%；50 GB/s 同批次接近不变。16 请求代理 MTP8 在 100 GB/s 高延迟下慢约 1.7%。两项运行规则都不会在这些较大 batch 启用，仍需继续检查新增分支对代码生成/调度的影响。PCIe 代理 MTP1 16 请求也有 5%–8% 回退，原地读同样变慢，结合前几轮的 Host 链路波动，不宣称该场景没有回退。

原推荐 f32 参数也逐格检查：真实 assistant MTP1 四请求 88.99→82.80 µs（约快 7%）；单请求 64.48→65.19 µs（慢约 1.1%）。代理 f32 四请求只快约 3.8%，因此不能把 f16 四请求的约 18% 改善说成相对旧版所有调参最优的收益。完整表含两模式的每个慢格子，见 [`final_results.md`](../temp/sim_link/tune_latency/final_results.md) 和 [`反向复测`](../temp/sim_link/tune_latency/final_repeat_results.md)。

同次朴素方法对照中，100 GB/s＋20 µs 的真实 assistant MTP1 四请求本文约 85.8 µs、Memcpy+LRU 92.6 µs；单请求约 65.1 / 65.0 µs，接近持平。MTP8 四请求约 252.1 / 246.8 µs，仍慢约 2%；16 请求约 669.3 / 865.4 µs。CPU LRU 和 PCIe CPU gather 仍不计时，朴素 attention 仅用于 GPU 计时，不做数值校验。全部每步命中率、误差、两下限和比值在 [`comparison_results.md`](../temp/sim_link/tune_latency/comparison_results.md)。

最终旧新、原推荐参数、大 batch、反向复测、计算下限和朴素对照合计 150 个 batch 配置、19992 段有效入队检查；本文两模式共 74448 次 launch 的逐步采样行校验通过，max abs 0.007677。筛选与全部候选共 107 份成功计时 JSON；`manifest.json` 区分最终证据及候选，并保存文件/源码哈希。不能把早期复用 prepare 计数的原型数据当最终实现的证据。

完整测试覆盖原有路径，以及新完成计数在空行后复用、64/128 头、staging 不足及 host_split 关闭时的边界。旧/新性能对照固定 f16/h64、4096 槽、7 次冷启动；代理为 64K/32 连续位置，assistant 为四段完整 64K/1024 窗口。MTP1 是 1024 步，MTP8 是 128 步。全部使用每 32 步的入队检查，段间保留 LRU；失败段所在 pass 从冷状态重测，不保留受污染样本。

下限 b 是相同 trace/形状正常构建纯 HBM attention 的最好实测样本；下限 a 为逐步 max(b, 去重未命中字节/链路带宽) 的稳态平均。固定访问延迟未计入 a，它是乐观下限；比值直接计算，不截断。50 GB/s 的部分 batch 传输下限已经高于纯计算下限，这部分差距需要降低实际未命中字节才能消除。

脚本、逐步样本、未采用补丁和源码哈希在 `temp/sim_link/tune_latency/`。`run.py` 跑常规矩阵；`confirm.py` 从 git 读取上一版 header，复测后恢复候选；`finish.py` 检查完整正确性、补齐纯 HBM 下限、128 请求大 batch 和反向顺序复测。基线也使用相同的扩大后内部 workspace/launcher 检查，只有 kernel header 不同，不将 workspace 差异计为代码收益。H800 原三个硬件实验及两个新版验证仍排队，尚无本轮 H800 结果。
