# 远端 KV 稀疏 MLA 算子：模拟慢链路（带宽与延迟）测试

本文记录在本机 A100 上，用模拟方法把远端链路带宽降到 100、50 GB/s，以及在每次远端访问上附加 2～20 µs 延迟后，本文 kernel 与两种朴素方法（都开 LRU）的跨 decode 稳态性能，以及它们与两种理论下限的差距。所有数据由脚本生成，原始 JSON 与生成脚本见文末。

## 1. 结论

1. **链路变慢时，本文 kernel 的优势变大。** MTP8、≥ 16 请求时，本文为两种朴素方法中较快者的耗时比：不限速（262 GB/s）0.84～0.90，100 GB/s 0.68～0.74，50 GB/s 0.73～0.77。MTP1 ≥ 128 请求：不限速 0.81～0.88，100 GB/s 0.69～0.71，50 GB/s 0.78。
2. **最优配置随带宽改变。** 262 GB/s 时原地读最快；100 和 50 GB/s 时 staged（16 个 fetch CTA）最快，MTP8 128 请求时比原地读快 1.7 倍（100 GB/s）和 1.9 倍（50 GB/s）。原因是原地读对未命中页的每个引用各读一次远端（MTP8 稳态平均 2.1 次），链路慢时这些重复读成为瓶颈；staged 在全 batch 内去重，每页只读一次。
3. **离下限 a（max(计算, 传输)）：** 50 GB/s、MTP8 128 请求时为 1.06×，传输已基本跑满链路；100 GB/s 时为 1.24×。**离下限 b（纯本地计算）：** 随链路变慢从 1.43× 增大到 1.79×（100 GB/s）和 3.06×（50 GB/s），这部分差距是链路本身的代价，开 LRU 后每步仍有约 15% 的条目要过链路。
4. **附加延迟 ≤ 5 µs 基本无影响**；带宽越低，对延迟越不敏感（50 GB/s 时延迟从 0 增至 20 µs，MTP8 128 请求耗时只从 7606 变为 7634 µs）。
5. **高带宽 + 高延迟时本文变慢**：不限速、附加 20 µs 时，MTP8 128 请求本文 5275 µs，Memcpy+LRU 4254 µs（慢 24%）。原因是本文的在途读请求量不足以掩盖 20 µs（需要约 20 µs × 262 GB/s ≈ 5 MB 在途）；Memcpy 的 GPU gather 用 432 个 CTA 同时在途。可通过增加 fetch CTA 或预取深度改进，尚未实施。
6. **小 batch**：MTP8 4 请求不限速时为朴素较快者的 1.31 倍、100 GB/s 时 1.14 倍，50 GB/s 时反超（0.93）；MTP1 16 请求不限速时 1.13 倍，100 和 50 GB/s 时均为 0.90。

## 3. 模拟方法

### 3.1 为什么不用背景流量抢带宽

最初尝试在 GPU1 上运行 SM 写 kernel 或 copy engine 拷贝，持续向 GPU0 写入（`temp/sim_link/bgload.cu`），占用 GPU1→GPU0 方向的 NVLink。实测 GPU0 的随机 gather 带宽最低只能降到 132～134 GB/s，无论背景流量多大。链路在「GPU0 读请求的返回数据」和「GPU1 主动写入的数据」之间大致五五分配，因此到不了 100 和 50 GB/s。copy engine 背景流量对 GPU0 的读几乎没有影响（仍为 263 GB/s）。该方法放弃。

### 3.2 设备端链路模拟器

模拟代码集中在 `include/flashinfer/attention/far_link_emu.cuh`，只有定义 `FLASHINFER_FAR_EMU` 时才编译进去；否则所有钩子为空宏。正常构建的 SASS 与修改前逐字节相同（两个 MLA 模块都比对过），71 项单元测试通过。

模型：全 GPU 共用一个「虚拟链路时钟」。每次远端读按字节预约：

- 开始时刻 = max(链路时钟, 发出时刻)；链路时钟 += 字节数 ÷ 目标带宽（`atomicAdd`；链路空闲时先把时钟推到当前时间，避免积攒空闲额度）。
- 数据可用时刻 = 开始时刻 + 字节数 ÷ 目标带宽 + 附加延迟。

真实读请求照常立即发出（真实 NVLink 比模拟链路快），只是使用数据前要等到可用时刻（`%globaltimer`，纳秒全局时钟）。因此多个请求可以同时在途，行为接近一条真实的「低带宽 + 高延迟」链路，而不是串行化每个请求。

各方法的接入点（三种方法用同一个模拟器）：

| 方法 | 远端读的位置 | 钩子 |
|---|---|---|
| 原生 MLA kernel（Direct、计算下限） | `load_kv`：每个 tile 的远端行 | 加载时累加该 tile 的远端字节；等待该 tile 时（`cp.async` wait 之后、barrier 之前）预约并等待 |
| 本文 kernel，原地读 | `load_host_batch_kv`：attention 直接读远端行 | 同上 |
| 本文 kernel，staged | fetch CTA 读一块（16 或 64 行）远端页 | 每块累加字节；fetch CTA 使用该块前预约并等待 |
| Memcpy | GPU gather 未命中页到本地 | 专用 gather kernel（`temp/sim_link/emu_gather.cu`，432 个 CTA，每 CTA 16 行）读完一组后预约并等待，再写出 |

「远端」的判定：本文 kernel 用页号 ≥ `host_page_start`；原生 kernel 和 gather 用地址是否落在远端那段 VMM 映射内。

### 3.3 每次测试前的验证

每档设置运行前，用模拟 gather 实测带宽（1.2 GB 随机行），并用单 CTA 依赖读（下一行地址取决于上一行数据）实测延迟，要求带宽误差 ≤ 5%、延迟误差 ≤ 10%（+0.6 µs）。全部通过：

| 设置 | 实测带宽（GB/s） | 实测依赖读延迟（µs） |
|---|---:|---:|
| 不限速，0 µs | 255.5 | 0.96 |
| 100 GB/s，0 µs | 100.0 | 1.44 |
| 50 GB/s，0 µs | 50.0 | 1.47 |
| 不限速，+2 / 5 / 10 / 20 µs | 255.3 / 253.9 / 252.3 / 258.4 | 2.05 / 5.16 / 10.26 / 20.56 |
| 100 GB/s，+2 / 5 / 10 / 20 µs | 99.9 / 99.9 / 99.9 / 99.7 | 2.05 / 5.20 / 10.31 / 20.55 |
| 50 GB/s，+2 / 5 / 10 / 20 µs | 50.0 / 50.0 / 50.0 / 50.0 | 2.05 / 5.16 / 10.28 / 20.53 |

另用 kernel 本身验证：原生 kernel 128 请求、30% 远端（725 MB 远端引用），50 GB/s 时实测 14.53 ms，理论 14.50 ms；100 GB/s 时 7.31 ms，理论 7.25 ms。

### 3.4 模拟器自身的开销

模拟构建、不限速时与正常构建的耗时比（跨 decode 稳态）：

| 方法 | MTP8（4～128 请求） | MTP1（16～256 请求） |
|---|---:|---:|
| 本文 原地读 + LRU | 1.10～1.11 | 1.11～1.16 |
| 本文 staged + LRU（8 CTA） | 1.03～1.08 | 1.03～1.05 |
| Memcpy + LRU | 1.10～1.12 | 1.10～1.11 |
| Direct + LRU | 1.03～1.12 | 1.08～1.11 |
| 原生 kernel，全本地 | 1.13～1.15 | 1.13～1.15 |

开销来自每个 tile 的等待点，所有方法都受影响。因此**本文与两种朴素方法都在同一个模拟构建下测**，相互比较公平；**下限 b（纯本地计算）用正常构建测**，不含这部分开销，对本文偏保守。

## 4. 测试设置

| 项目 | 设置 |
|---|---|
| 模型参数 | GLM-5.2 风格 DSA sparse MLA：BF16，576 维（1152 B/token/层），top-k 2048，64 头 |
| top-k 索引 | 回放 DeepSeek-V2-Lite 代理 trace（真实 attention 分数的 top-2048），64K 上下文，`temp/mtp_overlap/rounds_ctx65536_*.pt` |
| KV 放置 | 除每个请求最新 token 外全部在远端（GPU1 HBM） |
| 跨 decode | 32 个连续 token（MTP8 为 4 步，MTP1 为 32 步），取后一半步的每步中位数平均；3 次冷启动 pass |
| LRU | 每请求一个池，4096 槽；同一套 LRU 用于所有方法 |
| batch | MTP8：4、16、64、128 请求（32～1024 行）；MTP1：16、128、256 请求 |
| 计时 | CUDA event，只计 GPU 执行 |

### 4.1 比较对象

| 方法 | 是否开 LRU | 远端怎么读 | 说明 |
|---|---|---|---|
| **本文，原地读**（`ours_inplace`） | 开 | attention CTA 直接读远端（UVA + VMM 统一地址），不去重 | 命中读缓存；认领未命中页的行把 tile 落地后 shared memory 里的数据写入 LRU victim 槽 |
| **本文，staged 8 / 16 CTA**（`ours_stage`） | 开 | 8 或 16 个 fetch CTA 在全 batch 去重后读远端，写入 HBM staging | 命中读缓存；fetch CTA 同时把页写入 victim 槽；attention 先算本地 tile，远端 tile 等就绪标志 |
| **Memcpy + LRU**（`memcpy_lru`） | 开（CPU 上提前算好，不计时） | 每步把未命中页 GPU gather 到本地（模拟链路上），再跑原生 kernel | 先搬后算，串行 |
| **Direct + LRU**（`direct_lru`） | 开（CPU 上提前算好，不计时） | 原生 kernel：命中读本地，未命中原地读远端；随后 GPU gather 未命中页进缓存 | 每个未命中页至少读两次远端 |
| 下限 a | — | — | max(纯本地计算, 本步去重后的未命中字节 ÷ 链路带宽)；未命中数取本文 kernel 的实测值，不限速行按 262 GB/s |
| 下限 b | — | — | 纯本地计算：原生 kernel，所有选中行在本地 HBM，零传输，正常构建 |

「本文最优」取各本文配置中最快者。表中「本文 ÷ 朴素较快者」= 本文最优 ÷ min(Memcpy+LRU, Direct+LRU)。

## 7. 局限

- 模拟器只模拟「总带宽上限 + 固定附加延迟」，不模拟真实链路的拥塞、排队和带宽随访问模式的变化（例如 PCIe 小包效率）。
- 模拟构建有 3%～16% 的钩子开销（第 3.4 节），各方法都在同一构建下比较；下限 b 不含该开销。
- 朴素方法的 LRU 记账在 CPU 上提前算好，不计时，对它们偏宽松。
- top-k 是 DeepSeek-V2-Lite 代理 trace，跨 decode 只有 32 个 token；真实 GLM-5.3 trace 采集中。
- 只在 NVLink 远端（GPU1 HBM）上模拟；Host DRAM 远端（PCIe）的模拟未做。
