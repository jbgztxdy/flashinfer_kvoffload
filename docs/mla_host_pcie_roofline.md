# 突破 PCIe 瓶颈：量化分析与可选路径

批量 Host 直访 kernel（[mla_host_batch_kernel.md](mla_host_batch_kernel.md)）在大 batch 下已经把计算掩盖了 83%～88%，实测只比 `max(传输, 计算)` 高 3%～9%，调度层面基本到顶。本文回答：剩下的瓶颈是什么，能怎么突破。

## 1. 瓶颈的量化模型

单个（query 行，选中 token）的两侧成本：

| | 量 | A100 + PCIe 4.0 |
|---|---|---|
| 计算 | QK 64 head × 576 + PV 64 head × 512 = 139 kFLOP | 峰值 0.45 ns，**实测 1.37 ns**（1024 行，峰值的 33%） |
| 搬运 | 1 个 token 的 KV | BF16 1152 B → **42.7 ns** @ 27 GB/s |

算术强度 **121 FLOP/B**。机器比值（峰值算力/PCIe）= 11,556 FLOP/B，相差 96 倍。

定义**可完全掩盖的 Host 命中率** `f* = c / (u × B/PCIe)`，其中 c 是每 key-row 计算耗时，u 是去重率，B 是每 token 字节数：

| Query 行 | c (ns) | u | f* |
|---:|---:|---:|---:|
| 1（旧单 batch kernel） | 13.52 | 1.00 | **31.7%** |
| 8 | 2.74 | 0.448 | 14.3% |
| 64 | 2.17 | 0.429 | 11.9% |
| 1024 | 1.37 | 0.408 | **7.9%** |

**f\* 随 batch 增大而下降**：工作量两边都线性增长，但小 batch 时 GPU 没填满（1 行只跑到峰值的 3.3%），计算时间由固定开销决定、几乎不随 batch 变，而传输时间严格线性。这解释了为什么旧报告中 batch=1 时「20% 命中接近全本地」——那是把传输藏进了 GPU 的空转时间，不是可推广的结论。

模型验证：1024 行时实测 = `max(计算, 传输)` 的 1.03～1.09 倍。

## 2. 已排除：CPU 侧计算（ScoutAttention 路线）

[ScoutAttention](https://arxiv.org/html/2603.27138v1) 的核心论据是「36 核 CPU 的 attention 吞吐约 100 GB/s，远高于 PCIe 的 15 GB/s，所以应该算而不是搬」。**这个结论在 MLA 上反转**：

| 架构 | 每 token KV | 每 token-row FLOP | 每头触及维度 | 算术强度 |
|---|---:|---:|---:|---:|
| GQA（64 q 头 / 8 KV 头 × 128） | 4096 B | 32.8 kFLOP | 256 | **8 FLOP/B** |
| MLA（64 q 头共享 1 份 latent） | 1152 B | 139 kFLOP | 1088 | **121 FLOP/B** |

15.1 倍的差距由两个因素相乘，各占一半：

- **每头触及的维度多 4.25×**。MLA 在 decode 用 absorbed 形式——K/V 的上投影被吸收进 query，所以每个头直接在 512 维 latent + 64 维 RoPE 上做 QK、在 512 维 latent 上做 PV（1088 维），而 GQA 每头只在 128 维头空间里做（256 维）。**不是「少算了投影」，而是把投影折进 query 后在更宽的空间里算。**
- **每 token 字节少 3.56×**。GQA 的一份 KV 被 8 个 q 头共享，MLA 的 latent 被全部 64 个共享。

4.25 × 3.56 = 15.1 = 121/8。与实测吻合：1024 行时 101.6 TFLOPS / 841 GB/s = 121 FLOP/B。DeepSeek-V3 的 128 头配置强度达 **242 FLOP/B**。

这两件事是同一枚硬币的两面：MLA 用「更少字节 + 更多计算」换同等质量——正是它适合卸载的原因（字节少），也正是 CPU 侧计算不适用的原因（算力需求高）。

本机实测（2× Xeon Gold 6530，64 核，AMX-BF16）：

| 测法 | 耗时 | 达到算力 |
|---|---:|---:|
| 8192³ BF16 GEMM（可达上限） | 83.9 ms | 13.1 TFLOPS |
| 逐行 bmm，1024 行 × 614 token | 104.7 ms | 0.8 TFLOPS |
| 按请求组批 `[512,576]×[576,1200]` × 128 | 220.9 ms | 0.8 TFLOPS |
| 对比：搬 KV 过 PCIe | **6.6～10.9 ms** | |

**三条路径不要混淆**（本机全部实测）：

| 路径 | 实测 |
|---|---:|
| PCIe 4.0 ×16（GPU 跨总线读 host DRAM） | 27 GB/s |
| CPU 读自己的本地 DRAM（单 socket，NUMA 本地） | **240 GB/s** |
| CPU BF16 算力（8192³ GEMM） | **13.1 TFLOPS** |

前两者是**不同的总线**，27 与 240 并不矛盾：CPU 侧算 attention 读的是本地 DRAM，不走 PCIe。

受什么限制，看「DRAM 带宽 × 算术强度」与算力的比较：

| 架构 | 跑满 DRAM 所需算力 | 算力允许的 KV 消费速率 | 受限于 |
|---|---:|---:|---|
| GQA（8 FLOP/B） | 1.9 TFLOPS | 1638 GB/s | **DRAM 带宽**（CPU 充裕） |
| MLA 64 头（121） | 29.0 TFLOPS | 108 GB/s | **算力**（CPU 稀缺） |
| MLA 128 头（242） | 58.1 TFLOPS | 54 GB/s | **算力** |

**能否打平 PCIe**（1024 行、30% 命中）：PCIe 搬去重后的 177 MB 需 6.6 ms；CPU 必须算满 88 GFLOP（1024 行 × 614 token），要在 6.6 ms 内完成需 **13.4 TFLOPS = 本机峰值的 102%**。即**完美效率下恰好打平，零余量**；实测 0.8 TFLOPS（峰值的 6%），慢 17 倍。

反直觉的推论：**跨行去重帮 GPU 路径多于帮 CPU 路径**。每个唯一 token 平均服务 4.1 个 query 行，去重让字节 ÷4.1（PCIe 受益）而 FLOP ×1（CPU 不受益）。所以无去重时 CPU 只需 3.3 TFLOPS 即可打平，我们的 kernel 做了去重后门槛升到 13.4 TFLOPS。

结论：**对 MLA，CPU 侧算 attention 不是正确工具**——不是因为 roofline 差一个数量级，而是最好情况恰好打平、实际差 17 倍，且 CPU 还要服务其他工作。

注意 CPU 是多用户共享的（attention 测量时 load average 25，DRAM 测量时 3.5），小 GEMM 另有约 13 ms 固定开销，实测值偏悲观；但「完美效率恰好打平」只依赖峰值算力，不受影响。

**澄清：CPU 侧的瓶颈是算力，不是它自己的内存带宽。** CPU 的本地 DRAM 有 240 GB/s，但 MLA 每读一个字节要做 121 FLOP 的工作，CPU 先把算力用完了：

| CPU 侧的候选瓶颈（1024 行，30% 命中） | 量 | 速率 | 耗时 |
|---|---:|---:|---:|
| DRAM 读（去重后，cache blocking） | 177 MB | 240 GB/s | 0.74 ms |
| **算力** | 88 GFLOP | 13.1 TFLOPS | **6.68 ms** ← 瓶颈 |

**算力比 DRAM 紧 9.1 倍——CPU 远远用不满自己的内存带宽。** （工作集检查：每请求 KV 1.3 MiB + query 0.6 MiB ≈ 1.9 MiB，L2 2 MiB / L3 约 160 MiB，cache blocking 可行，所以 DRAM 只需读去重后的 177 MB。）

前文那个「108 GB/s」= 13.1 TFLOPS ÷ 121 FLOP/B，含义是**算力允许消费未去重字节的速率**，是算力的换算而非内存带宽。roofline 取两者较小值：

| 架构 | 算力换算 | DRAM | 实际可达 | 受限于 |
|---|---:|---:|---:|---|
| GQA（8 FLOP/B） | 1638 GB/s | 240 GB/s | 240 GB/s | **DRAM 带宽** |
| MLA（121 FLOP/B） | 108 GB/s | 240 GB/s | 108 GB/s | **算力** |

这就是架构差异的全部：GQA 在 CPU 上能用满 240 GB/s 的内存带宽，MLA 只能用到 108 GB/s 等效，因为算力先耗尽。

于是两条路径几乎持平：**CPU 路径（算力限制）6.68 ms，GPU 路径（PCIe 限制）6.55 ms**。另一种等价说法是把 CPU 换算到去重字节口径：13.1 TFLOPS ÷ (121 × 4.1 复用) = 26.4 GB/s，对比 PCIe 的 27 GB/s。

**那么 CPU 和 GPU 两条路并行能否相加？** 可以，但增益有限，因为 CPU 路径自己也要占 PCIe：

| 每行的 PCIe 代价 | |
|---|---:|
| GPU 路径：搬去重后的 KV | 169 KB |
| CPU 路径：query 送出 72 KB + partial output 送回 64 KB | **136 KB** |

MLA 的 query 很大（64 头 × 576 维），正是因为它让 64 个头共享一份 KV。所以 CPU 路径只省 **1.24×** 的 PCIe 字节，而非此前文档中错写的 4.4×（那个数漏算了 query 的传输，且用了未去重的 KV 作分母）。

按行拆分、两条路共享同一条 PCIe 的最优点：

| 方案 | 耗时 |
|---|---:|
| 纯 GPU 路径 | 6.55 ms |
| **最优混合（82% 行交给 CPU）** | **5.52 ms（1.19×）** |
| 纯 CPU 路径 | 6.68 ms |

**约 1.2 倍，且前提是 CPU 完全空闲。** 在真实服务节点上 CPU 还要跑 MoE 专家（KTransformers 路线）、调度、采样，这点增益会被挤掉。相比之下 FP8（1.76～2×）和跨步缓存（稳态 3.8×）都更大且不占 CPU。结论：**混合方案理论上成立但性价比低，不建议优先做**；若换到 CPU 算力更强或互连更快的平台（Grace Hopper）需重新评估。

## 3. 最大的杠杆：KV 量化格式（我们 benchmark 用的是最宽的那种）

我们所有 benchmark 都用 BF16（1152 B/token）。这是**有效但最保守**的选择：目标栈里 FP8 是受支持的可选模式，不是默认值，也不是我们"用错了格式"。

- vLLM 的 sparse MLA 后端（`temp/dsa_sources/vllm_flashinfer_sm90.py`）：`supported_kv_cache_dtypes = ["auto", "bfloat16", "fp8", "fp8_e4m3"]`，注释写明「FP8 cache 直接读取（HBM 流量减半），在 shared memory 里转成 BF16，query 保持 BF16」。
- FlashMLA 的 `is_fp8_kvcache` 默认 `False`，同样是可选项。

所以这是一个**尚未启用的 1.76～2 倍杠杆，需要一次精度评估**。各格式：

| 格式 | B/token | 相对 BF16 | f*（1024 行） |
|---|---:|---:|---:|
| BF16（**我们所有 benchmark 用的**） | 1152 | 1.00× | 7.9% |
| V3.2 FP8+sparse（512×e4m3 + 16 B scale + 128 B BF16 RoPE） | 656 | 1.76× | 13.8% |
| V4 FP8 | 584 | 1.97× | 15.5% |
| V4.1 FP8（RoPE 也量化） | 528 | 2.18× | 17.2% |
| 直接 fp8_e4m3（vLLM 后端已支持，576 维全量化） | 576 | 2.00× | 15.8% |
| V4.1 FP4（e2m1，**仅 V4.1 的 `extra_k_cache`**） | 288 | 4.00× | 31.5% |

**我们文档里的传输量和 f\* 都是 BF16 下的保守值。** 启用 FP8 后 f\* 从 7.9% 提到约 14%～16%。

V3.2 的 656 B 和 V4.1 的 288 B 是 DeepSeek 特定格式，表明这条线的演进方向；对 GLM 类目标，直接可用的是 vLLM 后端已支持的 `fp8_e4m3`。FP4 在参考实现里限定「只用于 `extra_k_cache`」，即一个二级 KV 缓存——这个设计看起来正是为分层/卸载准备的，但属于 V4.1 才有的能力，**不能作为 V3.2 / GLM 类模型的选项**。

## 4. 第二大杠杆：跨轮次复用（实测）

此前测的 0.41 去重率是**一轮内** 8 个 MTP token 之间的。对持久化缓存而言，真正的问题是**轮与轮之间**。用同样的方法抓取 4 个连续 verify 轮（`--mtp 32`）后实测：

| | 远端 token 已在缓存中 | 新增搬运（相对轮 0） |
|---|---:|---:|
| 轮 1 | 54.6% | 48.9% |
| 轮 2 | 68.1% | 33.5% |
| 轮 3 | 73.5% | **26.6%** |

相邻两轮重合 55.7%，且随缓存变大继续改善。**稳态下持久化 HBM staging 缓存只需搬 27%，即 3.8 倍削减。** 容量需求可控：4 轮后每请求约 4191 个 token，128 请求在 FP8 下 336 MiB、FP4 下 147 MiB，A100 40GB 放得下（需要淘汰策略）。

## 5. 综合：30% 命中能否掩盖

1024 行、30% 命中，GPU 计算 2873 µs：

| 方案 | 搬运 | vs 计算 | 可掩盖 |
|---|---:|---:|:---:|
| 现状：BF16 + 仅轮内去重 | 10952 µs | 3.81× | ✗ |
| 改用 V3.2 FP8 | 6237 µs | 2.17× | ✗ |
| V3.2 FP8 + 持久化缓存 | **1659 µs** | 0.58× | ✓ |
| *（仅当目标采用 V4.1 分层格式）* FP4 不加缓存 | 2738 µs | 0.95× | ✓ |
| *同上* FP4 + 缓存 | 728 µs | 0.25× | ✓ |

**冷启动修正**：表中「缓存」行是**稳态**（约 3 轮之后）。轮 1 的新增搬运是 48.9% 而非 26.6%，此时 V3.2 FP8 + 缓存为 6237 × 0.489 = 3050 µs > 2873 µs 计算，**尚不可掩盖**。连续批处理下任何时刻都有一部分请求处于轮 0～1，实际收益介于冷热之间。

**FP8 + 持久化缓存（稳态）即可达标，约 1.7 倍余量**，可以支撑更高命中率或更慢的后端（SSD，见 `docs/kernel_goal.txt` 第 3 项）。

## 6. 建议的工程顺序

1. **启用 FP8 KV**（1.76～2×）。vLLM 的 sparse MLA 后端已支持 `fp8_e4m3` 并在 shared memory 里反量化，我们 kernel 的 staging 和 fetch 按字节数参数化即可。需要一次精度评估——这是可选模式而非默认值。
2. **持久化 staging 缓存**（稳态 3.8×）。**先看 [HiSparse](https://arxiv.org/pdf/2608.07009) 的 SGLang 实现再决定是否自建**——它已经做了 GPU 侧固定缓存 + LRU + 融合取数 kernel，并在 DSA 上评测。我们的差异化部分是在其之上叠加 MTP 轮内去重（2.4×，正交）。
3. **最近 4K 窗口常驻 HBM**。实测约 45%～47% 的选择落在这个窗口内，这部分根本不该放 Host——属于放置策略，不是 kernel 改动。
4. **小 batch 的固定开销**（8～64 行时 1.2～2.3 倍余量，全在延迟上）：0% 命中时跳过多余阶段、合并 grid barrier、小 batch 绕过 HBM staging 直入 shared memory。

硬件视角：PCIe 5.0 让 f\* 翻倍到 16%；Grace Hopper 的 NVLink-C2C（450 GB/s）使 f\* 达到 131%，这个问题整体消失。

## 7. 相关工作（修正：此方向文献活跃，不是空白）

**本文早期版本称「文献全部面向 MHA/GQA，未处理 MLA」，这是错的**，来自一次 GQA 关键词的搜索。针对 MLA/DSA 再查后，实际图景：

| 工作 | 做法 | 与本项目的关系 |
|---|---|---|
| [HiSparse](https://arxiv.org/pdf/2608.07009) | KV 全量留 host，GPU 侧固定大小缓存，**命中检测 + LRU 淘汰 + host→device 取数融合进一个 CUDA kernel，跑在 decode CUDA graph 内**。在 DSA/NSA/Quest 上评测，**已合入上游 SGLang**，吞吐最高 4.7× | **就是本文第 6 节建议的「持久化 staging 缓存」，已经做完并上线了。不应重新造。** 明确未覆盖 MTP / 投机解码 |
| [SparDA](https://arxiv.org/pdf/2606.04511)（NVIDIA） | 新增 Forecast 投影预测下一层所需 KV 块，跨层 lookahead 预取；**persistent UVA kernel + batch-adaptive CTA 分配** | CTA 分配策略与我们的 `fetch_ctas` 扫描等价。**已给出 batch 缩放的交叉点论述**（见下）。GQA/8B，明确把 DSA/MLA 列为 future work（因模型规模） |
| [ScoutAttention](https://arxiv.org/html/2603.27138v1) | CPU 侧算 attention 代替搬 KV，层超前预计算 | 第 2 节已实测排除（MLA 上算术强度反转） |
| [InfiniGen](https://medium.com/byte-sized-ai/llm-inference-optimization-accelerating-long-context-generation-with-kv-cache-offloading-to-cpu-12d3bea407d8) | 用 hidden state 作跨层代理预取 | SparDA 的直接前身 |
| NOSA / [SparseServe](https://arxiv.org/pdf/2606.04511) | UVA 同步传输 / working-set 感知的 batch 调整 | 减少传输量而非隐藏延迟 |
| IndexCache / [HISA](https://arxiv.org/pdf/2603.28458) | 跨**层**复用 top-k 索引 / 层次化索引降低选择开销 | 针对 token 级 DSA，但优化的是 selection 而非传输 |
| [KTransformers](https://github.com/kvcache-ai/ktransformers)（SOSP'25） | **反着做**：MLA/KV 留在 GPU，把 MoE 专家卸载到 CPU | 主流观点是「MLA 的 KV 足够小，不该卸载」。在 ~139K 上下文内成立；1M 上下文下每请求约 70 GB，该前提失效 |
| [KV Offloading 瓶颈分析](https://arxiv.org/pdf/2601.19910) | 系统分析卸载阈值，指出 MLA 的 70 KB/token 相对 GQA 的 192～328 KB 有 2.7～4.7× 优势 | **想评测 MLA 但因实现困难未能完成** |

**必须收回的两个「贡献」声明：**

1. ~~f\* 随 batch 下降的框架~~ — SparDA 第 4.3 节已有定性论述：「小 batch 时 GPU 未充分利用、层执行主导关键路径；batch 增大时层执行时间**次线性**增长（SM 占用改善）而预取量**线性**增长，超过交叉点后预取成为新瓶颈」。我们的增量只是把它在 MLA 上量化（f\* 31.7% → 7.9%，附实测常数），不是新框架。
2. ~~持久化 staging 缓存是待建的最大杠杆~~ — HiSparse 已实现并合入 SGLang。我们测到的跨轮复用数据（稳态 26.6%）是对其有效性的独立佐证，不是新方案。

**剩下确实未被覆盖的：**

1. **MTP × 卸载**。HiSparse 明确未处理 MTP / 投机解码；所有卸载工作都假设单 token decode。而 verify 轮内 8 个 MTP token 共享约 59% 的页（实测去重率 0.41 = 2.4× 削减）——**这是只有 MTP 场景才存在的杠杆**，且与 HiSparse 的跨步缓存正交，两者可叠加。我们的 kernel 已在 kernel 内实现了这层去重。
2. **MLA 的算术强度反转**（121 vs GQA 的 8 FLOP/B，DeepSeek-V3 的 128 头为 242）：GQA 在 CPU 上受 DRAM 带宽限制（CPU 充裕），MLA 受算力限制（CPU 稀缺），使 CPU 侧计算从 GQA 文献的主推方案变成错误工具。附带一个反直觉结论：跨行去重帮 GPU 路径多于帮 CPU 路径，因为它减字节不减 FLOP。有 roofline 论证 + 本机三项实测。SparDA/ScoutAttention/HGCA 均为 GQA。
3. **真实 DSA indexer 的 top-k 跨 decode 轮局部性**实测（轮内 0.41、相邻轮 55.7%、稳态 26.6%）。IndexCache 测的是跨**层**索引复用，不是跨**步**。

规模上，这是「在已有系统上补一块 MTP 相关的缺口」，不是开辟新方向。宜作为内部报告或 workshop 短文，**不应包装成新系统**。

## 8. 四个「无损突破 PCIe」提案的评估（已实测）

针对一组外部提出的无损方向，用 DeepSeek-V2-Lite 的真实 MLA latent 实测后的判断：

### 方向一：跨层 latent 残差熵编码 —— **前提不成立，已证伪**

假设是「相邻层同一 token 的 latent 高度相似，残差熵低」。实测（27 层 × 2048 token 的真实 latent）：

| 层间隔 | 余弦相似度 | 残差范数 / 原始范数 |
|---:|---:|---:|
| 1 | **0.002** | **1.388** |
| 4 | 0.001 | 1.239 |
| 同层相邻 token（对照） | 0.392 | — |

**相关性为零，残差比原始向量还大 1.39 倍**——编码残差会让字节变多。

原因是架构性的：每层有各自独立的 `kv_a_proj_with_mqa` 投影，层 l 的 latent 是 `W^(l) h^(l)`，层 l+1 是 `W^(l+1) h^(l+1)`。即便 hidden state 因残差连接而相似（InfiniGen 正是利用这一点做**选择**），两个 latent 也处在互不相关的基底中。**InfiniGen 用 hidden state 预测重要性可行，不代表 latent 本身可做跨层残差压缩**——提案混淆了这两件事。

附带一个工程死结（即便相关性成立也无解）：DSA 每层选择的 token 不同。若层 l 存为相对层 l−1 的残差，要重建层 l 的某个 token 就必须同时取到层 l−1 的同一 token——而那个 token 这一层未必被选中。为 30% 的命中额外拉取基准层，很可能净亏。

### 方向二：无损「推测—验证」 —— **逻辑自相矛盾**

若草稿用**无损**压缩的 KV，解压后与全精度逐位相同，则草稿输出 ≡ 验证输出，接受率恒为 100%——验证步骤纯属多余，直接用压缩 KV 即可。推测—验证框架的收益**来源于草稿比验证便宜**，而这要求草稿有损（VeriCache 正是如此）。无损前提下该方向退化为方向四，没有独立内容。

### 方向三：CPU 端按「头」划分算部分和 —— **在 MLA 上严格劣于纯 GPU**

提案认为「CPU 接 k 个头，只回传 k×512 的部分和」。但 **MLA 的 64 个头共享同一份 latent**：GPU 只要还算任意一个头，就仍需该 token 的**完整** latent。按头划分**完全不减少 GPU 的 KV 传输**，只是额外增加 CPU 的往返：

| CPU 接管 | GPU 仍搬 KV | CPU 往返 | 总 PCIe |
|---:|---:|---:|---:|
| 8/64 头 | 177 MB（不变） | 18 MB | 1.10× |
| 32/64 头 | 177 MB（不变） | 71 MB | 1.40× |
| 56/64 头 | 177 MB（不变） | 125 MB | 1.71× |

这与 GQA 完全相反——GQA 每个头组有自己的 K/V，分头即分 KV。提案把 GQA 的代价结构套到了 MLA 上，而它自己引用的「MLA 读一次 latent 服务所有头」恰恰是该方案失效的原因。正确的切法是**按 token / 按行**切（第 2 节已算，1.19×，且需 CPU 完全空闲）。

### 方向四：链路层无损浮点压缩 —— **方向成立，但上限只有 1.43×**

实测真实 BF16 latent 的逐符号熵：

| 部分 | 熵 | 可压缩性 |
|---|---:|---|
| 符号 + 指数（高 9 位） | 4.19 / 9 bit | 2.15× |
| 尾数（低 7 位） | **6.97 / 7 bit** | **1.00×（几乎是随机位）** |
| 合计 | 11.16 / 16 bit | **理论上限 1.43×** |

通用压缩器实测：zlib 1.30×、lzma 1.46×（已达到甚至略超逐符号熵上限，因其能捕捉跨符号模式）。**提案引用的 2.7× 在这份数据上不可达**——尾数本质上是随机的，这是浮点激活值的普遍性质。

即便取 1.43×，还要求 GPU 侧解码器持续吞吐 27 GB/s 输入 / 39 GB/s 输出，并与 attention 争抢 SM。考虑到第 1 节已测得 attention 本身只跑到峰值的 33%，再分走 SM 的代价不可忽略。**1.43× 的上限不足以支撑这个复杂度。**

### 对照：同样严格无损、但更大的三个杠杆

| 杠杆 | 倍数 | 依据 | 状态 |
|---|---:|---|---|
| 跨 decode 轮持久缓存 | **3.76×** | 实测稳态新增 26.6% | HiSparse 已实现并进 SGLang |
| MTP 轮内去重 | **2.45×** | 实测 u = 0.408 | **我们的 kernel 已实现** |
| 最近 4K 窗口常驻 HBM | **1.85×** | 实测 45% 选择落入 | 属放置策略 |
| —— 四提案中最好者（链路压缩） | 1.43× | 本次实测熵上限 | 不建议 |

这三项都是**纯放置/缓存，输出逐位不变**，不需要任何精度评估，而且相互正交、可以相乘。在严格无损约束下（即排除 FP8），它们才是应该投入的方向。

**总体建议：四个方向都不值得优先投入。** 方向一和方向二（提案建议优先的两个）分别被实测证伪和逻辑自洽性所否定；方向三在 MLA 上会让情况变差；方向四上限 1.43× 且实现复杂。需要注意的是，这四个方向的论证都建立在「把 GQA 的直觉套用到 MLA」之上，而 MLA 的两条特性——**每层独立投影**（否定方向一）和**全部头共享 latent**（否定方向三）——恰好使它们失效。

## 9. 跨轮持久缓存：实测（替代第 4 节的推算）

第 4 节的 3.76× 是按跨轮复用率推算的。现用**页放置模拟**实测：每个 position 在 HBM 和 Host 各有一份内容相同的副本，缓存命中走 HBM 地址、未命中走 Host 地址，输出逐位不变、只有 PCIe 流量不同。索引取自真实的 4 个连续 verify 轮。

1024 行（128 请求 × 8 MTP），30% Host 命中，µs：

| | miss | Direct | Memcpy | **我们的 kernel** |
|---|---:|---:|---:|---:|
| 无缓存 | 28.9% | 25912 | 13080 | **10996** |
| 缓存 轮 0 | 28.9% | 25941 | 13018 | **10925** |
| 缓存 轮 1 | 9.3% | 8549 | 7654 | **5491** |
| 缓存 轮 2 | 6.0% | 5554 | 6053 | **3912** |
| 缓存 轮 3（稳态） | 5.5% | 5320 | 5655 | **3492** |

稳态相对无缓存：Direct 4.87×、Memcpy 2.31×、**我们 3.15×**。Direct 受益最大（它原本每个引用都搬一次），Memcpy 最少（本就做了批内去重）。缓存后我们仍最快，相对 Memcpy 的优势从 1.19× 扩大到 **1.62×**。

**最关键的一条**：稳态 3492 µs vs 纯 attention（全 HBM、零传输）2592 µs = **1.35×**。即在 30% Host 命中下，持久缓存 + 我们的 kernel 几乎把 PCIe 完全掩盖——剩余 35% 还包含去重准备和 grid barrier 的固定开销。这是项目最初的目标。

局限：(1) 只测传输收益，**不含缓存管理开销**（命中检测、LRU 淘汰），HiSparse 称其接近零但我们未独立验证；(2) 模拟的是**无界缓存**，真实 LRU 有容量上限会更差；(3) 实测 miss 率（5.5%）低于按复用率推算的 26.6%，因为本实验中 Host 驻留按 position 固定、反复命中同一批 token，真实系统分层会变化。**故 3.15× 应读作上界。**

数据：`temp/host_attention_rounds/rounds128.json`。

## 10. 27 GB/s 确认是上限（零碎 gather 不损失带宽）

此前文档引用「低命中率时只有 18～22 GB/s」，暗示零碎访问有 gather 惩罚。**这是误读**，已修正。

控制变量实验（固定搬 288 MiB、固定并发，只改访问模式）：

| 模式 | GB/s |
|---|---:|
| 顺序（连续 288 MiB） | 27.0 |
| 随机，池 4.5 GiB | **27.0** |
| 跨步 16 行（每 18 KiB 取 1152 B） | 27.0 |
| 随机页排序后访问 | 27.0 |

并发 108～864 block 均稳定 27.0，**完全无 gather 惩罚**。原因是每行取满 1152 B 连续字节，已足以摊薄 TLP 包头，并复用页表项。

那个 22.6 GB/s 来自旧 benchmark 的**启动开销**而非带宽：它固定 2048 个 top-k，命中率越低搬得越少、耗时越短，2.2 µs 的固定开销占比越大（10% 命中搬 231 KiB 仅 12.2 µs）。扣除后为 23.7～26.6 GB/s。

27.0 GB/s = PCIe 4.0 ×16 理论值（31.5）的 86%，是 TLP 开销后的正常水平。**我们的 kernel 在大 batch 下已达 26.8 GB/s，即上限的 99%——传输侧没有剩余空间。**

## 11. 其余「突破 PCIe」想法的评估（含一个新的无损思路）

### CPU 分担（按行切）——缓存后失效

| 场景 | 纯 GPU | 最优混合 | 收益 |
|---|---:|---:|---:|
| 无缓存 | 6.55 ms | 5.51 ms（82% 行给 CPU） | 1.19× |
| **有持久缓存（稳态）** | 1.25 ms | 1.25 ms（**0% 给 CPU**） | **无** |

CPU 路径每行固定要 136 KB 的 PCIe 往返（query 72 KB + 部分和 64 KB）。缓存把 GPU 侧字节砍到 9 KB/行后，这个固定开销反而成为劣势。**第 2 节「1.19×」的结论在叠加缓存后作废。**

### 改计算形式（un-absorbed）——不减字节

un-absorbed 形式在 GPU 上先把 latent 上投影成每头 K/V。**搬运的仍是同一份 latent，字节完全相同**，只改变 GPU 端算力分配。对 PCIe 无效。

### 新思路：用 softmax 结构做「可证明可跳过」—— **已证伪**

这是本轮唯一一个原创的严格无损思路：`output = Σ softmax(s_j) v_j`，若能在**不读 v_j** 的前提下证明 token j 的权重低于 BF16 舍入下限，则跳过它不改变结果。这不是近似——是数值上严格等价。

前提一（分布偏斜度）**成立**：用真实 MLA query 和 latent 实测，top-2048 内有 **90.6%** 的 token 权重低于 BF16 相对舍入下限 2⁻⁸。理论上界 10× 削减。

前提二（上界紧致度）**不成立**。要证明需要分数上界，唯一不读 v_j 就能算的是 Cauchy-Schwarz：`s_j ≤ |q||k_j|`（Host 侧预存 |k_j| 仅需 2 B/token）。实测 **bound/actual 中位数 12.7×**，而这个误差发生在 exp() 的**指数位**上：权重上界被高估 e^11.7 ≈ **1.2×10⁵ 倍**。即便某 token 的真实权重小 10⁵ 倍，上界也判不出来。

**实测可证明跳过的比例：0.0%。**

这个负面结果本身有价值：它说明「无损跳过」这条路不是实现问题，而是**数学上封死的**——任何不读取 v_j 的上界都至少要经过范数放缩，而 exp() 会把放缩误差放大成天文数字。要绕过它只能读 v_j 的一部分（例如前 64 维算近似分数），但那就回到有损的两阶段 rerank。

### 汇总

| 方案 | 收益 | 无损 | 状态 |
|---|---:|:---:|---|
| 跨 decode 轮持久缓存 | **3.15× 实测** | ✓ | HiSparse 已实现 |
| MTP 轮内去重 | **2.45× 实测** | ✓ | **我们已实现** |
| 最近 4K 窗口常驻 | 1.24× 边际 | ✓ | 大部分被缓存覆盖 |
| 链路无损压缩 | 1.43× 上限 | ✓ | 复杂度高于收益 |
| CPU 分担（按行） | 1.19× → 缓存后 1.00× | ✓ | 缓存后失效 |
| FP8 KV | 1.76～2× | ✗ 需精度评估 | vLLM 已支持 |
| 两阶段 rerank | 1.5～2.4× | ✗ 丢 softmax 尾部 | — |
| 跨层残差编码 | 残差反而更大 | — | 已证伪 |
| 按头切给 CPU | 劣于纯 GPU | — | MLA 共享 latent |
| 无损推测—验证 | 逻辑矛盾 | — | 无损草稿 ≡ 验证 |
| 界限跳过 | 0.0% 可证明 | — | **本轮证伪** |

**在严格无损约束下，可做的已经做完了。** 持久缓存（3.15×）+ MTP 去重（2.45×，已实现）后，稳态离纯计算只有 1.35×，PCIe 基本被掩盖。再要突破必须放宽约束：FP8（1.76～2×，vLLM 已支持、只需一次精度评估）是性价比最高的下一步。

## 12. 本文结论的边界

- `f*` 是**无推测**的悲观下界：只考虑 attention 内部的掩盖窗口（2.6 ms）。真实前向中，`indexer(L+1)` 到 `attention(L+1)` 之间还有 MLP 的时间；若采用 InfiniGen/ScoutAttention 式的 query 预测，窗口可以进一步前移到 `MLP(L)`。具体能前移多少取决于 DSA indexer 的数据依赖，本文未评估。
- 跨轮复用样本量有限（2 份文档、9 个层、16 组、4 个连续轮），以 DeepSeek-V2-Lite 的真实 attention 作为 DSA indexer 的代理。足以支撑方向判断，不足以作为精确参数；需要用真实 indexer 的 trace 复核。
- CPU 侧测量在共享机器上完成（load average 25），是悲观值；roofline 上界不受影响。
- 两阶段重排（用 indexer 已有的分数对 Host 子集排序、只取 top-m）未评估。它不需要额外计算，但会丢掉 softmax 尾部，需要精度实验。
