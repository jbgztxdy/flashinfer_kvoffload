# A100 第三轮：单 query 的分块合并（2026-10-29）

本轮针对 MTP1 单请求的固定开销，基线为 `aeca4403`（kernel 与上一轮 `614655f1` 相同）。继续保留一个 cooperative kernel 和精确 LRU，缓存容量、top-k 和模拟器均未改变。新路径只在 **`num_rows == 1`** 时启用；MTP8 单请求有 8 行，使用原合并路径。

## 改动及筛选依据

原合并把一个 head 的 512 个输出维度分给 64 个线程，一个 CTA 同时处理四个 head。单 query 只有 64 个 head，只能让 16 个 CTA 合并，未充分利用 A100 的 108 个 SM。新路径给每个 head 一个 CTA，四组线程分别合并不同的分块状态，最后经 shared memory 合并 float 状态，输出和 LSE 的含义相同。每组批量预读四个状态以重叠独立的 L2 访问，复用 kernel 原有的动态 shared memory。

`%globaltimer` 阶段诊断显示，小 batch 的 prepare/resolve/同步约占 10 µs，合并尾部约 8–15 µs。诊断构建会改变代码生成，并且单步 CPU 发射使 event 耗时包含空隙；只用它定位阶段，正式性能均取未插桩构建。插桩补丁、逐 CTA 时间戳在 `temp/sim_link/tune_small/`。

筛选中保留所有失败和回退：

- 将每线程合并宽度从 8 缩至 2/4，没有稳定收益，未采用；首个候选有 `max` 类型重载导致的编译失败，修正后才测量，失败没有计时 JSON。
- 让最多 8 行都用四组并行合并，MTP1 单请求快约 5%–7%，但四请求和 MTP8 单请求慢约 3%–7%。批量预读没有消除多行回退，最终收窄为单 query。
- 代理 trace 和真实链路中的其他格子仍有测量波动，全部旧/新数据保留；不宣称所有 batch 都加速。

## 验证与复现

最终对照使用分段入队计时：每 32 步预先入队，段间同步但不重置 LRU，每个 pass 冷启动一次，保存每段的 CPU 入队时间、GPU 等待保护区和成功判据。1024 步一次排队会遇到 CUDA 队列回压，原长 trace 的部分 event 样本包含 CPU 发射间隙，导致 NVLink 单请求 staged 出现 60–90 µs 的不稳定值。简单延长等待保护无法解决队列回压，失败试验保留日志；旧 `single_query_*` / `base_repeat_*` 长 trace 数据不作为最终性能结论。最终表采用 `guarded_candidate_*` / `guarded_base_*`，所有保留 pass 的每段都通过入队检查。
