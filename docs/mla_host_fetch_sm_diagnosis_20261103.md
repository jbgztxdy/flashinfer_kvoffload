# 100GB/s差距诊断：fetch CTA的计算资源代价

当前证据支持：**在GPU3的MTP8/R128/LRU4096形状下，fetch长期占用24个SM是100GB/s差距的主要来源之一，而且很可能是主因。** 不是用108/84线性比例推算，而是新做了相同attention实现、相同真实remap/缓存载荷的84/108 CTA对照。仍不能把全部正式差距精确归因到这一项。

生产host/math/FAR保持cab508dc/34af/8507eab0；未安装优化，未改模拟器、正式参考或计时。正式v2结果仍为100GB0/20µs下3327.371/3360.555µs，逐步参考2701.022/2701.192µs，高23.19%/24.41%。本轮是诊断，不计为加速。

## 同实现84/108 CTA对照

独占GPU3/A100-PCIE、NUMA1，同卡独立far-HBM模拟，非NVLink。BF16、h64、K2048、MTP8/R128、LRU4096、staged/f24/item64/split off，前256位置/32步。每一步先运行完整kernel，再基于它产生的remap、staging与实际cache载荷，重放当前PV feature attention。

两个重放分支在同一个诊断kernel二进制内，仅运行attention的CTA数不同，均计算全部1024行输出；108个cooperative CTA在grid barrier后才允许闲置CTA退出，SMID记录证实108个不同SM。重放不执行prepare/fetch/LRU，也不更新epoch/cache metadata；它是计算容量对照，**不能作为优化后的端到端时间或替换正式device参考**。完整kernel退出会清零两个行长度游标，因此重放从kv_indptr恢复这个无padding trace的精确2048长度；该修正在任何GPU对照前完成。

| 同一attention实现 | 平均 µs | 三pass平均 µs |
|---|---:|---|
| 108个计算CTA | 2442.389 | 2431.264 / 2451.872 / 2444.032 |
| 84个计算CTA | 3047.989 | 3029.504 / 3063.872 / 3050.592 |
| 84相对108的代价 | **605.600，慢24.80%** | 每pass均约0.60–0.61ms |

每步交替84/108顺序，84先/后平均3049.707/3046.272µs，108先/后2441.899/2442.880µs，差异远小于0.606ms主信号。192次重放的全部输出逐元素一致、state全部一致；最终524288个有效缓存槽全载荷一致。完整诊断kernel平均3322.240µs，与正式3327.371µs接近。

正式0µs差距626.349µs与对照605.600µs同量级，说明计算资源影响足以解释主要量级；**不能据此声称96.7%的正式差距已经严格归因**。真实fetch CTA会在中途加入计算，重放则固定84/108个计算CTA；重放没有并行fetch的HBM/L2竞争、原ready等待及prepare/cache操作，静态行分配还包含整行负载均衡效果。

fetch CTA平均只承担约5%的输出，而如果从一开始平分计算，其24/108份额约22%。它们绝大部分launch时间都在推进读取/复制/缓存和限速等待，直到很晚才参加attention。24个fetch CTA占用时间合计59469.984/60036.000 SM·µs，除以108为550.648/555.889µs的全GPU服务机会成本。这与84/108对照0.606ms相互支持，**不是可直接扣除的墙钟收益**。

0µs实际unique载荷平均247.966MB，纯字节预算约2479.659µs，fetch跨度2523.392µs，差约43.733µs；20µs实际247.941MB、预算2479.409µs、跨度2552.672µs，差约73.263µs。因此没有证据表明0.6ms主要丢在“没有跑到100GB/s”。这仍是软件到达模型：实际取数额外消耗同卡HBM/L2，不能等价物理链路。

## 另外几项及不能做的相加

前置prepare/resolve约0.19ms在attention/fetch之前，确有优化价值，但即使全部消除，也小于当前达到110%还需的0.36–0.39ms。

fetch结束后的0.66–0.70ms是仍在执行的attention尾部，不能称为纯等待，也不能再与0.606ms容量损失相加：两者描述的是同一调度过程的不同视角。最后ready至fetch返回约4µs，排除了“大段延迟cache写回拖住fetch”的解释。LRU item累计平均2518/2475 SM·µs（每108SM约23µs）也是重叠工作，不能直接作为串行时间。

暖步骤每步约26/31次wait调用真的经历未ready轮询，而不是上万次ready检查都阻塞；首冷步约1542/1471次。wait总计数包含已经ready的检查及插桩，且warp计时不能观测全部CTA barrier时间，不能用来精确扣除“等待损失”。尾部CTA不均衡仍有约0.20ms的108SM折算未分配区间，但这只是预算恒等式，包含已退出CTA等空隙，尚未证明整段可消除。

## 为什么交界带宽更难

同形状下，100GB/s每步实际miss字节/带宽约2.48ms，正常device约2.56ms，24/32步计算主导。理想参考假设搬运和完整计算资源可以同时使用；现实则在接近整个计算窗口内留下84个初始计算CTA，它们的同实现容量实测约3.05ms。资源竞争在此交界区最容易暴露。

当带宽低到搬运远长于计算时，计算资源损失更容易被搬运覆盖，残余前后开销的百分比也被更大参考稀释。足够高的带宽使fetch更早结束，24个CTA能更早回来计算。这个机制解释预期趋势，**本轮没有重扫v2的50GB/不限速曲线，也不能声称物理NVLink或所有batch都已接近参考**；旧SXM大batch仍有约22%差距的记录不能忽略。

这不意味着直接减少fetch CTA就会变快。历史fetch数量减少、提前退休、cofetch等均有失败证据：减小取数资源会降低有效搬运吞吐，或损伤attention的stage/寄存器布局。新诊断确认问题位置，没有推翻这些负结果，更不构成重做旧参数扫描的依据。

讨论后续机制时，优先要求它具体兑现以下至少一项：在保持实际100GB/s及必要字节下，降低fetch的SM服务成本；加快84个计算CTA内的真实attention；减少约0.19ms前置阶段或整行尾部。当前到110%需省0.36–0.39ms，任何机制都应先对这一数量级和端到端成本给出可检验预期。
