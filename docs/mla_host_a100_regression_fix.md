# A100：修复第四轮的大 batch 回退（2026-10-29）

第四轮 `5c44fd70` 的按行提前合并和取数阈值只在小 batch 启用，但大 batch 的 kernel 中仍保留判断这些条件的代码。100 GB/s＋20 µs、MTP8 128 请求的同参数复测可重复约 3% 的回退。本轮把这些条件改为编译期参数，在 launcher 按形状选择实例；**每次调用仍只启动一个 cooperative kernel**，LRU、缓存容量、top-k、带宽/延迟模拟器及 workspace 布局保持。

## 改动与证据

`ROW_MERGE` 模板参数沿 kernel、attention item、merge 和取数块选择传递。只有 staged＋缓存、query/head tile 数至多 32 的 launch 选择 `true`；其他 launch 选择 `false`。`false` 用 `if constexpr` 完全删去按行完成计数、fence、等待和小 batch 取数阈值，保留原 grid barrier 和取数规则。这样不再让大 batch 支付小 batch 逻辑对控制流和代码生成的影响。

代价是为两条路径分别生成编译产物，JIT 编译工作和模块体积增加；没有新增运行时 kernel launch，也没有改变 Python 接口。

模拟构建、A100 使用的 2-stage/32-KV tile 实例，反汇编指令数：优化前 `109b1c76` 为 **13544**，回退版为 **13800**，修复后的 `false` 实例为 **13544**。三者寄存器均为 246、stack/local 均为 0；因此不是寄存器溢出。其他两种编译 tile 配置的 `false` 指令数也恢复为优化前值。指令调度、寄存器编号及 shared memory 静态布局仍有差异，**不宣称 SASS 逐字节相同**。原始压缩反汇编、资源用量和哈希在 `temp/sim_link/fix_large/`。

首组复现（7 pass、fetch_ctas=16、host_item_entries=64、BF16/64 头、4096 槽/请求、100 GB/s＋20 µs）中，MTP8 的 128 请求由优化前 **5533.70 µs**、回退版 **5690.88 µs** 恢复到 **5541.38 µs**。16 请求由优化前约 848 µs、回退版约 862 µs 恢复到约 847 µs。单请求仍约 91 µs，相对优化前约 103 µs 的收益保留。这是相同进程矩阵顺序下的实测，完整反向复测表保存全部差异及两下限。历史记录中的 f16/h64 指取数 CTA 数和 Host item 长度，不是数据类型。

优化前在修复版之后反向重跑时，100 GB/s＋20 µs 的结果如下，单位 µs：

|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 / 8 | 101.89 | 90.62 | 90.62 | 0.889 | 49.15 | 49.15 | 1.84 | 1.84 |

随后再次按修复版→回退版顺序复测，128 请求分别为 **5529.60 / 5688.83 µs**，16 请求为 **850.43 / 863.74 µs**，确认改善可以重复。完整旧/新矩阵有 55 个配置、110 个模式格子；超过 32 行的 30 个格子中，修复版最慢的一格比优化前多 **0.47%**（物理 PCIe 原地读，MTP8 16 请求），原先约 3% 的大 batch 回退已消除。该结论限于所测矩阵，未测试的参数和 H800 尚需验证。

真实 assistant 100 GB/s＋20 µs 的小 batch 收益也保留：MTP1 单/四请求由 69.06/92.53 µs 改为 65.55/85.69 µs，分别快约 5.1%/7.4%；MTP8 四请求由 261.25 改为 251.38 µs，快约 3.8%。MTP8 16 请求为 667.07→667.68 µs，差约 0.09%。

回退修复并不等于达到纯 device 性能。表中大 batch 的传输下限 a 已高于计算下限 b，后续性能优化仍须减少实际传输和等待开销。所有更慢的格子也保留在 [`results.md`](../temp/sim_link/fix_large/results.md)。

## 验证范围

覆盖 100/50 GB/s＋20 µs、真实 NVLink 和 PCIe，两模式，MTP1/8，代理 trace 的 1/4/16/128 请求，以及四个完整 assistant 窗口的 64K/1024 连续位置。逐格记录每步输出采样误差、去重未命中、全部 7 pass、入队保护条件和源码哈希。不同请求数可能绑定不同真实窗口，逐格比较始终保持请求数、trace、seed 和参数相同。

已有完整测试同时覆盖两个编译路径。持久池测试额外覆盖 batch 从 48 行缩到 24 行、再恢复 48 行，在两个 kernel 实例之间共享同一缓存，验证槽位映射和输出；不开 staged 的实例也运行同一组检查。

**93 项完整测试通过，154.23 秒。** 相比上一轮新增两项参数用例，同时覆盖两个编译路径之间的持久缓存切换。

本轮保留 44 份成功 timing JSON、152 个配置、13552 段有效入队检查、411712 次计时 launch；采样行 max abs 为 0.006596。`manifest.json` 记录全部源码/结果 SHA、覆盖及早期候选误标后按源码 SHA 更名的经过；早期结果未当最终对照。`audit.py` 可重建两个补丁的源码并检查全部入队段连续性、样本数和引用校验，`report.py` 生成完整逐格表。

复现入口：`temp/sim_link/fix_large/compare_versions.py` 依次测优化前、回退版和修复版，保存编译器资源；`verify.py` 跑完整测试、优化前的完整反向矩阵，再重复修复版/回退版的关键场景。二者在异常时恢复当前修复 header，运行前确认 GPU0/1 空闲，并先归档既有输出（脚本拒绝覆盖 JSON）。H800 原有三个作业仍为 Priority，第三轮 assistant 两个作业仍等依赖；本轮仅同步报告、补丁及证据，不覆盖排队版本，不将 A100 证据替代 H800 实测。
