# 远端 KV 稀疏 MLA 算子：融合 LRU 后的 PCIe / NVLink 实测（A100）

本文是 H800 排队期间在本机 A100 上完成的全套测试：单步 batch 扫描（PCIe、NVLink，MTP8 和 MTP1），带跨 decode LRU 缓存的多轮测试，以及与 LRU 改动前版本的 A/B 回归。与 SGLang HiSparse 的对比需要 FlashMLA（SM90 起才支持），只能在 H800 上做，作业已排队，结果出来后写入 `docs/mla_host_h800_lru.md`。

## 结论

- **没有回归。** 关闭缓存时，与 LRU 改动前的 kernel（`52f289a1`）在同卡交替测试，差异在 −2%～+4% 之间，与基线两次测量之间的波动（最大 7%）同量级。
- **PCIe，单步，MTP8：** 远端占比 ≥5% 时，除 1 请求、5% 一格（65 µs，Direct 54 µs）外，每个格子都快于 Memcpy 和 Direct 中较快的那个；0% 时有调度开销（第 3 节）。256 行以上离理论下限 1.00～1.12×；8～64 行在 1.1～1.6×；8 行最差，为 1.6～1.9×。
- **PCIe，跨 decode 稳态，全部 KV 在 Host：** LRU 让耗时下降 2.0～2.5×（MTP8）和 1.8～5.6×（MTP1）。256 行以上离「未命中字节 ÷ 带宽」的下限只差 1%～5%。
- **NVLink（第 7 节，最新）：** 改为由 attention CTA 自己写回缓存、不再用 fetch CTA 之后，开 LRU 的跨 decode 稳态在 MTP8 ≥ 8 请求、MTP1 ≥ 64 请求时快于同样带 LRU 的 Memcpy 和 Direct（是两者较快者的 0.77～0.88 倍），离「命中读本地 + 未命中原地读」的实际下限 1.02～1.19×。小 batch 仍慢 9%～49%。
- **调参：** PCIe 用 staged 模式、8 个 fetch CTA；NVLink 用原地读模式（`host_stage=False`），不需要 fetch CTA。第 4 节里 NVLink 的 fetch CTA 结论已被第 7 节取代。

## 1. 测试设置

| 项目 | 设置 |
|---|---|
| GPU | A100-SXM4-40GB（GPU0）；远端层是 GPU0 的 PCIe 链路访问 NUMA0 pinned DRAM，或 GPU1 的 HBM（经 NV12 NVLink） |
| 实测远端带宽 | PCIe：DMA 27.0 GB/s，SM 随机 gather 24.6～26.3 GB/s；NVLink：DMA 281 GB/s，SM gather 262 GB/s |
| KV | BF16，576 维，每 token 1152 B；top-k 2048；64 头 |
| 索引 | 回放实测的 DSA 代理 MTP top-k（`temp/mtp_overlap/*ctx65536*`）。最近 4096 个位置始终在 HBM |
| 计时 | CUDA Graph 重复调用，取中位数；单步扫描每格 8 轮 × 2 组索引 |
| 代码 | `a000249d`（工作区仅 `decode.cuh` 多一个行尾空格，与本 kernel 无关） |

**理论下限**取 `max(KV 全在 HBM 时的 attention 耗时, 去重后的远端字节 ÷ 实测 gather 带宽)`。实测 gather 带宽略低于 kernel 实际达到的约 26.8 GB/s，因此个别格子的比值会低于 1（最低 0.93），可以视为已经贴着下限。

对比方法：
- **Memcpy**：CPU 先把去重后的远端行收集到 pinned 内存（这部分不计时），再 H2D 拷贝，然后跑原生 attention。NVLink 下改为 GPU 上做 gather，计入时间。
- **Direct**：原生 kernel 逐个引用原地读远端。
- **ours**：本 kernel，staged 模式；`batch:f24` 表示用 24 个 fetch CTA。

## 4. 跨 decode 稳态（LRU 缓存）

### 测试方法

- 每个请求用实测的连续 32 个 token 的 top-k：MTP1 共 32 步，MTP8 每步 8 个 token，共 4 步。
- 除最新 token 外，全部 KV 放在远端，与 HiSparse 的设定相同；每请求 4096 个缓存槽。
- 每次 pass 都从冷缓存开始，取后一半步的平均作为稳态值。MTP8 只有 4 步，所以它的稳态只来自第 2、3 步，偏保守。
- 下限：
  - **计算下限**：KV 全在 HBM 时的 attention 耗时；
  - **传输下限**：本步未命中的去重字节 ÷ 实测带宽。

**NVLink 离下限远的原因：**
- **fetch CTA 吞吐不够：** NVLink 下传输下限只占计算下限的 20%～55%，瓶颈是 fetch CTA 本身。
  - 8 个 fetch CTA 时，128 请求、MTP8 要 7.74 ms；
  - 增加到 24、48、80 个时分别是 3.54、3.28、3.62 ms。
  - 再多的 fetch CTA 会挤占 attention 的 SM。
- **MTP1、1～4 请求时，有缓存反而比「全部远端原地读」慢**（0.62～0.98×）：带缓存路径有约 20～30 µs 的固定开销（prepare、两次 grid barrier、LRU item、缓存写入），而 NVLink 上原生原地读本身只要 39～63 µs。
  - 缓存是「远端占比 ≤30%」这个前提的来源（稳态每步未命中只占引用的 8%～19%），不能关掉；需要的是压掉这部分固定开销。

单步扫描（远端占比 10%～30%，作为缓存稳态的代理）里，最优 fetch 数随 batch 变化：1～8 请求 f8，16～64 请求 f16～f32，128 请求 f48。此时我们只在 8～16 请求快于 Direct（0.94～0.98×），128 请求时比 Direct 慢 3%～11%，小 batch 慢 30%～70%；对 Memcpy 在 16 请求以上大多更快。这个代理里朴素方法不含自己的缓存管理开销（真实系统需要类似 HiSparse 的 swap-in kernel），H800 上的 HiSparse 对比会给出含该开销的结果。

PCIe 上 8 个 fetch CTA 已经跑满链路：f4 明显变慢，f8、f16、f32 相差不到 2%。
- **改进方向：** 让 fetch 更高效（单个 CTA 内更多请求在途、减少每个 chunk 的同步），或让 attention item 直接从远端读未命中的页，同时把缓存写回交给空闲的 CTA。

- **MTP8 下每请求 4096 槽偏小：** 一步要选 8 × 2048 个 token，去重后每请求大约 2500～4000 个，4096 槽装不下两步的工作集。
- **PCIe 对容量最敏感：** 耗时基本与未命中数成正比。
- **显存代价：** 8192 槽 × 1152 B ≈ 9.4 MiB / 请求 / 层；128 请求、78 层时约 92 GiB。在单卡上无法对每层都开到这个容量。

## 5. 推荐配置

| 远端层 | 模式 | fetch CTA |
|---|---|---:|
| PCIe | `host_stage=True`，开缓存 | 8 |
| NVLink | `host_stage=False`，开缓存（attention CTA 写回，第 7 节） | 不用 |

缓存容量按显存预算设。MTP8 下每请求 4096 槽时，PCIe 稳态加速约 2.1×；8192 槽时约 3.8×。

## 6. 局限

- 本文是 A100 的数据。H800 是 PCIe Gen5（带宽约是 A100 的两倍），NVLink 带宽和 SM 数也不同，结论需要在 H800 上复核。
- 跨 decode 测试只有 32 个连续 token；MTP8 只有 4 步，稳态样本少。
- top-k 是 DSA 代理（DeepSeek-V2-Lite 的 attention），不是 GLM-5.2 indexer 的真实 trace。
- 0% 远端时，部分 batch 规模下有 18%～23% 的调度开销（第 3 节）。

## 7. NVLink：attention CTA 写回缓存（`03b11a2b`、`5f2e7e5b`）

### 为什么换方案

单个 SM 对远端的未完成读请求大约只有 40 KB，按 NVLink 约 2 µs 的延迟算，每个 fetch CTA 最多约 21 GB/s（`temp/fetch_bw/` 实测：在途数据量、线程数、每 SM 的 CTA 数都改变不了这个上限）。要喂满 262 GB/s 至少要 12～13 个 SM 只做搬运，而且每个未命中页要从远端读两次（fetch 一次、attention 一次）。

### 现在的做法

1. **prepare：** 命中的条目改写成缓存槽并打时间戳；未命中的页按 CAS 认领，认领行的条目打上 `kHostBatchOwnerBit`，并记下这是该行第几个认领。原地读模式下不需要 resolve 遍历。
2. **LRU：** 在两次 grid barrier 之间，每个池由一个 CTA 选出 victim、打时间戳并完成绑定（`resident`、`slot_page`），同时把每个认领条目的 victim 写进 `entry_victim`。
3. **attention：** tile 加载时用 `cp.async` 把这一 tile 各行的 victim 一起预取到 shared memory。tile 落地后，认领行直接把 shared memory 里的这一行写到 victim 槽。远端只读一次，没有 SM 专门搬运，写回循环里也没有额外的全局内存访问。

数据正确性：缓存填满、开始淘汰之后，每个缓存槽的内容与远端原页逐字节一致（`temp/host_lru_dbg/dbg_peer.py`）；71 项单元测试通过；PCIe staged 路径与 `13f761fd` 交替对比无变化。

### 结果（跨 decode 稳态，全部 KV 在远端，每请求 4096 槽，µs）

### 两个下限

- **计算下限**（上表）：所有选中的行都在本地 HBM。原地读模式达不到它，因为 MTP 的 8 行会重复读同一页：MTP8 稳态每个未命中页平均被引用 2.1 次（128 请求时 704 MB 的引用对 336 MB 的去重页，`temp/lru_sim/miss_refs.py`；NVLink 计数器实测每步 687 MB）。704 MB ÷ 262 GB/s = 2.7 ms，已经超过 2.45 ms 的计算时间。
- **原地读下限**：原生 kernel 对同一批条目，命中读本地、未命中原地读，不做任何缓存管理（`temp/host_lru_dbg/ideal_inplace.py`）。ours 离它 1.02×（16 请求 MTP8）、1.08×（128 请求 MTP8）、1.13×（64 请求 MTP8）、1.19×（256 请求 MTP1）。剩下的是 prepare 和 LRU 的前置阶段，以及 launch 末尾的负载不均。

### 试过但没留下的

- **让重复引用读缓存里刚写好的副本**（每个槽一个 launch 标志）：只在 tile 提前读页号时检查，流量只降 7%（687 → 637 MB），反而慢 28%；同一请求的 8 行被同一波的 8 个 CTA 同时执行，检查时认领行的数据还没到。加有限次自旋等待后，流量只降 10%，耗时变成 5～30 倍。都已回退。
- **把 LRU 步交给最先到达的 CTA、去掉第二次 grid barrier**：大 batch 慢 2%～6%，已回退。
- **staged 模式加更多 fetch CTA**（第 4 节）：被本节方案取代，128 请求 MTP8 时 staged 最快 3.3 ms（48 个 fetch CTA），原地读写回 3.2 ms 且不占 SM。

### 还没解决的

小 batch（MTP8 1～4 请求、MTP1 ≤ 32 请求）仍慢于带 LRU 的朴素方法 9%～49%。原因是每个池的 LRU 步约 20～30 µs 在关键路径上（1 请求 MTP1 时 item 在第 28 µs 才开始，而原生 kernel 整步只要 33 µs）。和 PCIe 一样，小 batch 暂不处理。
